# Private PrintProfit owner dashboard

Implementation: `admin/index.html` and owner-only callable functions in `functions/admin.js`.
Status: built and tested locally; not deployed or connected to live reporting.

## Access model

The login uses the owner's email as the username, their Firebase password, and a six-digit TOTP from an authenticator. It deliberately has no hard-coded PIN, shared password or username-to-email lookup. A custom non-email username is not implemented.

Every admin API requires all of: the exact server-configured `PRINTPROFIT_ADMIN_UID`, verified email matching `PRINTPROFIT_OWNER_EMAIL`, password provider, a TOTP-authenticated token, authentication within the last hour, and a current enabled Auth record with the factor still enrolled. Revoked sessions are rejected. Missing configuration denies access. No browser role flag grants permission. All admin and billing collections remain inaccessible through Firestore client SDKs under the existing deny-all fallback.

The static login shell can be downloaded, including its source. Business data and controls require the server checks. Do not describe a static page as private hosting. There is no customer navigation link to it and it requests no search indexing. It does not load site analytics. The dashboard uses a separate Firebase app instance and memory-only persistence; refreshing it requires a new login.

## Deployment and setup

1. Use the existing sandbox first. Set `PRINTPROFIT_OWNER_EMAIL` and `PRINTPROFIT_ADMIN_UID` in its ignored `functions/.env.printprofit-test` file to the actual verified owner Auth record. Set production values separately; never guess a UID or commit email/credentials.
2. Enable Firebase Authentication with Identity Platform and TOTP. Check the project’s current billing/pricing before enabling the upgrade. Official instructions: https://firebase.google.com/docs/auth/web/totp-mfa . This is a project setting, not something the static page can enable. Preserve existing authentication providers.
3. Install dependencies and run `npm test --prefix functions`. Deploy the function codebase using `firebase.billing.json` and an explicit project. Keep both existing public billing enablement flags off until the separate live billing rollout is complete. The five admin functions have no Stripe-secret binding; deploying the whole existing codebase still requires the billing secrets. Use explicit selected function names if deploying only admin endpoints, and do not delete existing billing functions.
4. Verify deployed Firestore rules still deny direct access to `adminGrants`, `adminAffiliates`, `adminAudit` and all billing collections. The Admin SDK is the only access path. Review with the rules emulator before production; local tests in this change exercise handlers, not the deployed rules emulator.
5. Serve `admin/` alongside the site's existing public Firebase configuration on the test host. Sign in with the owner account, enrol its authenticator through the setup screen, then sign in again with password and code. The setup key is generated by Firebase and kept only in browser memory. It must never be copied to chat, logs or GitHub. Use the authenticator's secure backup/recovery facility. An authorised Firebase project administrator can reset a lost factor through Firebase's documented account-recovery process; there is no unauthenticated bypass in this dashboard.
6. Verify non-owner, signed-out, password-only, disabled, revoked and expired-session requests are rejected. Check grant, expiry and revocation against a verified sandbox recipient; ensure any paid subscription remains intact. Both the normal site login and account reauthentication now handle an enrolled authenticator.
7. Merge/deploy the frontend and backend together after sandbox verification. The intended initial route is `/admin/` on the existing site. An `admin.printprofit.co.uk` host is not configured: that would require a separate hosting target, appropriate Firebase authorised domains, a Firebase config path, CORS changes and DNS verification. Do not add the domain to CORS before it is controlled and ready.

## Reports

Subscription counts use existing Stripe webhook entitlement snapshots, exclude expired access and separate trials from active paid accounts. Estimated monthly recurring revenue uses the configured published GBP plan prices (£2.50/month and £24/year divided by 12). It is not cash received and does not deduct fees, refunds, tax or discounts. The screen shows the most recent webhook time; a webhook report is not a full Stripe reconciliation. Expired records are excluded, and missing records may undercount. The deployment still depends on the live billing rollout in `docs/live-pro-rollout.md`.

Traffic uses the Google Analytics Data API with the runtime service account and `analytics.readonly` OAuth scope. Set `PRINTPROFIT_GA_PROPERTY_ID` to the numeric GA4 property ID, enable `analyticsdata.googleapis.com`, and grant the deployed `adminTraffic` function's actual runtime service-account email Viewer access to that GA property. A `G-...` measurement ID is not the property ID. No downloaded service-account key is required. Dates cover 7, 30 or 90 completed days through yesterday in the property's timezone. The API returns visitors, sessions, page views, daily sessions and the top ten paths. Failures and missing connections display explicitly rather than as zero.

Affiliate reporting is manual in this version. Save one current snapshot per partner ID; reusing the ID replaces the snapshot and creates an audit entry. Enter the report's exact date range and currency (GBP/EUR/USD). Pending, approved but unpaid, and paid totals are distinct, and different currencies/periods are not summed together. Automatic Awin/other-network APIs, CSV import and historical charts are not implemented yet; these need each network's reporting permissions and verified definitions.

Complimentary access is stored separately from paid subscriptions. Grant/extend/replace or revoke it with a private reason. It is checked by `getProAccess`, and active complimentary access blocks new checkout. Existing paid billing continues until the subscriber cancels it. The existing public Pro browser flag still controls whether Pro gating is active; this work does not enable charging. Private notes never appear in customer access responses.

Overview queries fail explicitly above 5,000 records per collection rather than returning misleading partial totals. Audit writes and their corresponding changes are transactional. Audit history retains grant notes and account UIDs for operational review; establish a retention period before wider use.

## Verification and remaining gates

Node tests cover the owner/MFA gate, revocation/disablement, grant expiry and revocation, transaction audit writes, input validation, revenue separation and existing billing behavior. Syntax and workspace navigation checks pass. Browser QA checks the sign-in screen and layout only. Live TOTP, Google Analytics permissions, real Stripe reporting and deployed Firestore-rule enforcement need sandbox/live credentials and have not been verified here.
